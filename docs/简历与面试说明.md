# 简历与面试说明

定位为个人学习项目：基于已有Dify教学工作流进行业务场景改造和工程完善。Dify、DeepSeek、数据库插件和ECharts插件都是使用的现成组件，不能描述为自行研发的底层平台或大模型。

下面可作为项目表述的基础。Dify中已人工核对销售额、订单数、客单价，并生成柱状图；完整端到端验收尚未完成。尚未完成的内容不要写成已上线；测试数字只表达真实验证范围。

项目名称：商析助手——基于Dify的电商经营数据问答与可视化

技术栈：Dify / Python / MySQL / DeepSeek / ECharts

项目简介：面向电商经营分析场景，基于模拟客户、商品、订单和明细数据，构建自然语言提问到SQL查询、结果解释和图表展示的应用流程。

职责与实现：

- 设计四表电商数据模型及可重复生成的模拟数据，统一有效销售额、客单价、销量和退款率等指标口径，处理订单明细关联导致的金额重复统计问题。
- 基于Dify编排查询规划、Python代码检查、顺序查询、证据汇总及图表分支；对不明确的问题返回澄清，对缺失数据或不支持的能力明确说明。
- 实现SQL词法与规则检查、表/函数允许列表、单次100行和最多3条查询限制，并采用数据库只读账号限制实际权限；实现纯JSON、代码块及思考标签输出的兼容处理和图表参数校验。
- 建立23条验收问题和16条参考查询及独立期望结果，验证数据口径、异常分支和权限限制。端到端准确率及耗时需在Dify实际运行后填写。

目前已有的验证证据：11组本地检查通过；16条参考SQL在独立临时MySQL实例中执行通过；只读账号的DELETE、UPDATE和跨库读取三项拒绝检查通过。这些数字不代表大模型问答正确率。

## 面试应能解释的问题

1. 为什么使用四张表而不把所有数据塞进一张宽表？订单和明细分别是什么粒度？
2. 为什么JOIN之后可能重复计算销售额？如何验证修复？
3. 退款订单保留原付款额时，有效销售额如何计算？
4. 模型输出不是标准JSON时怎么办？为什么不能直接截取遇到的第一个`{...}`？
5. 为什么不能仅靠“只生成SELECT”的提示词保障数据库权限？
6. 本项目SQL检查器支持哪些语法、会误拒绝哪些合法SQL？
7. 数据库查询失败、查询为空和模型汇总失败有什么区别？
8. 如何区分参考SQL正确与模型生成SQL正确？如何设计后续评估？

应如实说明的边界：当前校验器是约束范围内的词法/规则校验，不是完整SQL语法树分析器；没有实现RAG、模型微调、自动纠错闭环、缓存、高并发服务或销售预测。没有实际企业用户、线上效果或真实业务收益。

后续优先改进：先跑完验收，记录失败类型与真实耗时；再考虑引入SQL AST解析、有限次数的SQL修复或按需检索数据库元数据。一次只增加一个可验证的功能。
